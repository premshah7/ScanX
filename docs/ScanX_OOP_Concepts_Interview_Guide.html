The 4 Pillars of OOP Mapped to ScanX
Core Theory + Real Code

🔒 1. Encapsulation

Bundling data and methods together, while restricting direct access to internal state to maintain invariants.
// lib/otp.ts // Internal state & hashing hidden // Only public methods exposed export async function generateOtp(...) export async function verifyOtpCode(...) // actions/device.ts // HttpOnly cookie write hidden from JS

🧩 2. Abstraction

Hiding low-level implementation details behind clean, high-level interfaces so callers only deal with concepts, not raw mechanics.
// Prisma ORM abstracts raw SQL await prisma.attendance.create(...) // Nodemailer abstracts SMTP protocol await sendEmail(to, subject, html) // pdf2json abstracts PDF stream parser await parsePdfToTable(buffer)

🧬 3. Inheritance / Extension

Reusing and extending base attributes and behaviors across specialized sub-domains without code duplication.
// types/next-auth.d.ts interface Session { user: { role: string; status: string; } & DefaultSession["user"] } // NextAuth base session extended // Schema: User 1:1 Student / Faculty

🎭 4. Polymorphism

Treating diverse object types through a shared interface, while each type executes specialized behavior dynamically.
// Session Model: // If session.subjectId -> Academic Attendance // If session.eventId -> Event Guest Check-in // Role Polymorphism: // getDashboardRoute(role) -> /admin, /faculty, // /student, /guest

GoF Design Patterns Used & Applicable in ScanX
System Design

1. Singleton Pattern Creational

📂 lib/prisma.ts & actions/settings.ts
Problem: Next.js hot-reloading in development instantiates a new PrismaClient on every file edit, rapidly exhausting the PostgreSQL connection pool.
OOP Solution: We bind the client instance to Node's globalThis singleton container so only one shared connection pool exists across the runtime.
Also used in SystemSettings where only one configuration row is ever instantiated in PostgreSQL.

2. Chain of Responsibility Pattern Behavioral

📂 actions/attendance.ts (The 9-Gate Pipeline)
Problem: markAttendance() contains 450 lines of sequential if (!gate) return error checks, violating the Single Responsibility and Open/Closed Principles.
OOP Solution: Each gate (Cookie Gate, Expiry Gate, IP Gate, Device Gate, Duplicate Gate) becomes an independent handler class in a pipeline. Each handler either passes to nextHandler.handle(req) or short-circuits with a failure result.

3. Strategy Pattern Behavioral

📂 lib/auth.ts (Authentication Strategies)
Problem: Authentication handles 3 totally different verification algorithms (Password bcrypt compare, OTP cryptographic lookup, and Guest bypass) inside nested switch/if statements.
OOP Solution: Encapsulate each algorithm behind an AuthStrategy interface (PasswordStrategy, OtpStrategy, GuestStrategy) selected dynamically based on user input credentials.

4. Factory Method Pattern Creational

📂 actions/session.ts & actions/auth.ts
Problem: Initializing sessions or registering users requires creating paired relational records (User + Student or User + Faculty) with conditional properties.
OOP Solution: A SessionFactory creates concrete AcademicSession or EventSession instances with proper foreign key assertions, ensuring callers never create invalid polymorphic records.

How to explain in an interview: "I refactor the 9 gates into the Chain of Responsibility Pattern. Each gate extends an abstract AttendanceGate class and handles one single validation."

// OOP Refactoring: Chain of Responsibility Pattern
abstract class AttendanceGate {
    protected nextGate?: AttendanceGate;

    public setNext(gate: AttendanceGate): AttendanceGate {
        this.nextGate = gate;
        return gate;
    }

    public async handle(context: AttendanceContext): Promise<GateResult> {
        const result = await this.validate(context);
        if (!result.success) return result; // Short-circuit on failure
        return this.nextGate ? await this.nextGate.handle(context) : { success: true };
    }

    protected abstract validate(context: AttendanceContext): Promise<GateResult>;
}

// Concrete Gate Handlers (Single Responsibility Principle)
class DeviceCookieGate extends AttendanceGate {
    protected async validate(ctx: AttendanceContext): Promise<GateResult> {
        return ctx.deviceId ? { success: true } : { success: false, error: "Device Cookie Missing" };
    }
}

class QrExpiryGate extends AttendanceGate {
    protected async validate(ctx: AttendanceContext): Promise<GateResult> {
        return (Date.now() - ctx.tokenTimestamp <= 4000)
            ? { success: true }
            : { success: false, error: "QR Code Expired" };
    }
}

class DeviceBindingGate extends AttendanceGate {
    protected async validate(ctx: AttendanceContext): Promise<GateResult> {
        if (!ctx.student.deviceHash) {
            await ctx.repo.bindDevice(ctx.student.id, ctx.deviceHash, ctx.deviceId);
            return { success: true };
        }
        return ctx.student.deviceHash === ctx.deviceHash 
            ? { success: true } 
            : { success: false, error: "Device Mismatch - Proxy Blocked" };
    }
}

// Assembling the Pipeline (Open/Closed Principle: Add new gates without editing existing ones!)
const attendancePipeline = new DeviceCookieGate();
attendancePipeline
    .setNext(new QrExpiryGate())
    .setNext(new AccountStatusGate())
    .setNext(new CampusIpGate())
    .setNext(new DeviceBindingGate())
    .setNext(new DuplicateCheckGate());

Strategy Pattern: Decoupling password, OTP, and guest authentication algorithms into interchangeable classes.

// Strategy Interface
interface IAuthenticationStrategy {
    supports(credentials: AuthCredentials): boolean;
    authenticate(credentials: AuthCredentials): Promise<AuthenticatedUser>;
}

// Concrete Strategy 1: Password Bcrypt
class PasswordAuthStrategy implements IAuthenticationStrategy {
    supports(c: AuthCredentials): boolean { return !!c.password && !c.otp; }
    async authenticate(c: AuthCredentials): Promise<AuthenticatedUser> {
        const user = await prisma.user.findFirst({ where: { email: c.email } });
        if (!user || !(await bcrypt.compare(c.password, user.password))) {
            throw new Error("Invalid credentials");
        }
        return new AuthenticatedUser(user);
    }
}

// Concrete Strategy 2: One-Time Password
class OtpAuthStrategy implements IAuthenticationStrategy {
    supports(c: AuthCredentials): boolean { return !!c.otp; }
    async authenticate(c: AuthCredentials): Promise<AuthenticatedUser> {
        const valid = await verifyOtpCode(c.email, c.otp);
        if (!valid) throw new Error("Invalid or expired OTP");
        const user = await prisma.user.findFirst({ where: { email: c.email } });
        return new AuthenticatedUser(user!);
    }
}

// Concrete Strategy 3: Guest Bypass
class GuestAuthStrategy implements IAuthenticationStrategy {
    supports(c: AuthCredentials): boolean { return c.isGuest; }
    async authenticate(c: AuthCredentials): Promise<AuthenticatedUser> {
        const user = await prisma.user.findFirst({ where: { username: c.username, role: "GUEST" } });
        return new AuthenticatedUser(user!);
    }
}

// Strategy Context Resolver
class AuthenticationService {
    constructor(private strategies: IAuthenticationStrategy[]) {}

    async login(credentials: AuthCredentials): Promise<AuthenticatedUser> {
        const strategy = this.strategies.find(s => s.supports(credentials));
        if (!strategy) throw new Error("Unsupported authentication method");
        return await strategy.authenticate(credentials);
    }
}

Domain Class Hierarchy: True Object-Oriented Polymorphism for academic subjects vs event sessions.

// Abstract Base Session Class
abstract class BaseSession {
    constructor(
        public readonly id: number,
        public readonly startTime: Date,
        public isActive: boolean
    ) {}

    public abstract calculateAbsentees(): Promise<StudentSummary[]>;
    public abstract canStudentAttend(student: StudentProfile): Promise<boolean>;
}

// Polymorphic Subclass 1: Academic Lecture Session
class AcademicSession extends BaseSession {
    constructor(id: number, startTime: Date, isActive: boolean, public readonly subjectId: number) {
        super(id, startTime, isActive);
    }

    public async calculateAbsentees(): Promise<StudentSummary[]> {
        // Enrolled students minus students in attendance table
        const enrolled = await prisma.subject.findUnique({ where: { id: this.subjectId } }).students();
        const attended = await prisma.attendance.findMany({ where: { sessionId: this.id } });
        const attendedIds = new Set(attended.map(a => a.studentId));
        return enrolled.filter(s => !attendedIds.has(s.id));
    }

    public async canStudentAttend(student: StudentProfile): Promise<boolean> {
        return student.isEnrolledInSubject(this.subjectId);
    }
}

// Polymorphic Subclass 2: Public Event Session
class EventSession extends BaseSession {
    constructor(id: number, startTime: Date, isActive: boolean, public readonly eventId: number) {
        super(id, startTime, isActive);
    }

    public async calculateAbsentees(): Promise<StudentSummary[]> {
        // Events do not calculate absent academic students
        return [];
    }

    public async canStudentAttend(student: StudentProfile): Promise<boolean> {
        const reg = await prisma.eventRegistration.findUnique({
            where: { eventId_userId: { eventId: this.eventId, userId: student.userId } }
        });
        return reg?.status === "APPROVED";
    }
}

SOLID Principles Breakdown in ScanX
Interview Evaluation
Principle Where Followed in ScanX Where Violated & How to Fix
S — Single Responsibility lib/otp.ts handles ONLY OTP generation and verification. actions/device.ts handles ONLY device cookie identity. actions/attendance.ts violates SRP by parsing tokens, checking IP, checking batches, binding devices, and logging proxies all in one function. Fix: Split into dedicated Gate classes.
O — Open / Closed NextAuth's provider architecture: adding a new OAuth provider (Google/GitHub) doesn't require modifying the core session callback flow. Adding a new attendance gate (e.g. Geolocation GPS Gate) requires editing the core markAttendance() method. Fix: Chain of Responsibility pipeline.
L — Liskov Substitution User role hierarchy: ADMIN, FACULTY, and STUDENT all satisfy the base User contract and can be authenticated through NextAuth interchangeably. GUEST users lack roll numbers and email domains, causing potential crashes if downstream functions expect full student academic properties without null checks.
I — Interface Segregation SessionView.tsx and Scanner.tsx receive segregated, minimal props rather than entire monolithic database models. The User model carries student, faculty, and guest fields all together. Fix: Separate IStudentProfile, IFacultyProfile interfaces.
D — Dependency Inversion NextAuth accepts abstract credentials providers rather than depending on a hardcoded Prisma database query. Server Actions directly instantiate and query prisma directly rather than depending on an injected IRepository abstraction. Fix: Implement Repository Pattern.

Q1 "Where did you use Object-Oriented Programming (OOP) in your project?"
💬 Interview-Ready Answer
"While Next.js uses functional React components on the frontend, our backend domain architecture relies on core OOP principles:
1. Encapsulation: In lib/otp.ts and actions/device.ts, we hide internal implementation details—like cryptographic random integer generation and HttpOnly cookie flags—behind a clean, restricted public interface.
2. Abstraction: Our database operations rely on Prisma's ORM classes, abstracting raw PostgreSQL joins and indexes behind strongly typed object models.
3. Polymorphism: In our session management, a single Session entity behaves polymorphically depending on whether it represents an academic class (subject-linked, batch-restricted, absent calculations) or a public campus event (open check-in, guest-allowed).
4. Design Patterns: We use the Singleton Pattern in lib/prisma.ts to maintain a single database pool across hot reloads, and the Strategy Pattern in our multi-flow authentication provider."
📂 Code Reference
lib/prisma.ts, lib/otp.ts, prisma/schema.prisma
Q2 "Explain the Singleton Pattern in ScanX. Why is globalThis required?"
💬 Interview-Ready Answer
"In lib/prisma.ts, we implement the Singleton Pattern to guarantee that only one instance of PrismaClient exists across the application runtime.

In Next.js development mode, hot module replacement (HMR) re-evaluates module files on every code edit. If we simply wrote export const prisma = new PrismaClient(), every file save would instantiate a new database connection pool, rapidly exceeding PostgreSQL's max connection threshold.

By caching the client on Node's global object: const globalForPrisma = globalThis as unknown as { prisma: PrismaClient }, the singleton survives module re-evaluations while remaining active across the entire application lifecycle."
📂 Code Reference
lib/prisma.ts L1-L9
Q3 "How would you refactor your 450-line markAttendance function using OOP?"
💬 Interview-Ready Answer
"Currently, markAttendance() executes 9 sequential procedural gates. It violates the Single Responsibility Principle (doing token parsing, IP verification, device binding, and proxy logging in one method) and the Open/Closed Principle (adding a 10th gate requires modifying this core function).

I would refactor this using the Chain of Responsibility Pattern:
1. Create an abstract base class AttendanceGate with a handle(context) method that calls nextGate.handle() on success or short-circuits on failure.
2. Implement discrete handler classes for each gate: DeviceCookieGate, QrExpiryGate, AccountStatusGate, BatchGate, IpGate, DeviceBindingGate, and DuplicateAttendanceGate.
3. Assemble the pipeline at bootstrap: cookieGate.setNext(expiryGate).setNext(deviceGate)....
This makes each validation unit-testable in isolation and allows adding new security gates (like a Geolocation Gate) without touching existing code."

Q4 "Give an example of Polymorphism in your database schema and business logic."
💬 Interview-Ready Answer
"Our Session model is polymorphic: it contains two mutually exclusive nullable foreign keys: subjectId (academic course) and eventId (public workshop/hackathon).

In business logic, this manifests as Subtype Polymorphism: - When an Academic Session is active, attendance checks verify batch enrollment, and session termination computes an absent list by taking the subject's enrolled students minus attendees. - When an Event Session is active, absent calculations are bypassed (since public events have no static roster), and attendance checks verify whether the user's EventRegistration was approved.

The caller interacts with a unified session entity, but runtime behaviors diverge depending on whether it is an academic or event session."
📂 Code Reference
prisma/schema.prisma L96-L108 & actions/session.ts L169-L182
Q5 "How is Encapsulation used to enhance security in ScanX?"
💬 Interview-Ready Answer
"Encapsulation is central to our security boundaries:
1. Device Cookie Encapsulation: In actions/device.ts, the generation and assignment of the device_id cookie is encapsulated on the server with httpOnly: true, secure: true, and sameSite: 'strict'. Client-side JavaScript is physically prevented from accessing or modifying this identifier.
2. OTP Logic Encapsulation: In lib/otp.ts, internal state details—such as the 5-minute expiry calculation, the 60-second cooldown query, and atomic deletion on verification—are encapsulated inside functions. Callers cannot manipulate expiration timestamps or bypass rate limits."
📂 Code Reference
actions/device.ts & lib/otp.ts
Q6 "Explain how the Open/Closed Principle applies to ScanX."
💬 Interview-Ready Answer
"The Open/Closed Principle states that software entities should be open for extension, but closed for modification.

- Where followed: NextAuth's authOptions.providers array. If we want to support Google OAuth or GitHub login tomorrow, we simply append a new provider instance to the array without editing the core session token generation or route callback logic.
- Where violated: In actions/attendance.ts, adding a new verification rule (e.g. WiFi BSSID verification) requires modifying the monolithic markAttendance() function. In our refactored architecture, implementing the Chain of Responsibility satisfies OCP by allowing new gates to be chained without modifying existing gate code."
📂 Code Reference
lib/auth.ts L7-L180
Q7 "How does the Strategy Pattern solve multi-path authentication in your project?"
💬 Interview-Ready Answer
"Our system supports three distinct authentication pathways: Password authentication, One-Time Password (OTP) verification, and Guest bypass.

Rather than having deeply nested conditional statements inside authorize(), the Strategy Pattern defines a common IAuthStrategy interface with a method authenticate(credentials). We have three concrete strategies:
- PasswordStrategy (hashes and compares with bcrypt)
- OtpStrategy (validates code against Otp table and enforces 5-min TTL)
- GuestStrategy (authenticates event attendees by username)

The provider context selects the appropriate strategy at runtime based on the credentials payload, decoupling validation logic from the session pipeline."
📂 Code Reference
lib/auth.ts L31-L178
Q8 "Inheritance vs. Composition: Which did you favor in ScanX and why?"
💬 Interview-Ready Answer
"We strongly favored Composition over Inheritance, which is the recommended practice in modern TypeScript and relational data modeling:

Instead of having Student and Faculty inherit from a base User class in the database (Table-per-Hierarchy inheritance), we used Relational Composition:
- A User has an optional 1-to-1 relationship with a Student record.
- A User has an optional 1-to-1 relationship with a Faculty record.

This avoids bloated tables with endless nullable columns and prevents rigid inheritance coupling. If an institution has a Teaching Assistant who is both a Student and Faculty member, composition allows a User to attach to both profiles without breaking an inheritance tree."
📂 Code Reference
prisma/schema.prisma L12-L65
Q9 "How would you apply the Dependency Inversion Principle to make your code testable?"
💬 Interview-Ready Answer
"Currently, our Server Actions directly import and call the concrete prisma singleton. This violates the Dependency Inversion Principle (DIP) because high-level business logic directly depends on a low-level database client, making unit testing impossible without an active PostgreSQL database.

To fix this, we introduce the Repository Pattern:
1. Define an interface IAttendanceRepository with methods like hasAttended(studentId, sessionId) and recordAttendance(data).
2. Implement PrismaAttendanceRepository for production.
3. For unit testing, inject a MockAttendanceRepository that stores records in an in-memory Map.
Now, our attendance service depends on an abstraction, not a concrete database tool."
Q10 "Where would a Factory Pattern be useful in ScanX?"
💬 Interview-Ready Answer
"In two key areas:
1. Session Creation (createSession): A SessionFactory.create(params) method encapsulates the complex validation logic required to ensure a session never has both a subjectId and an eventId, or neither. It acts as a factory producing properly initialized, valid session objects.
2. Bulk Student Ingestion (actions/bulk.ts): When parsing CSVs or PDFs, a StudentFactory maps unstructured raw table rows into sanitized User and Student entity pairs, assigning default passwords, generating enrollment keys, and formatting batch relations before sending them to PostgreSQL."

Q11 "Can you show where you used Abstraction in your third-party integrations?"
💬 Interview-Ready Answer
"We used abstraction across three major utilities:
1. Email Service (lib/email.ts): The caller simply executes sendEmail(to, subject, html). The caller has no knowledge of whether Nodemailer is using real SMTP credentials or falling back to development console logging when EMAIL_SERVER_USER is missing.
2. PDF Table Parser (lib/pdf.ts): Callers simply call parsePdfToTable(buffer) and receive normalized arrays of rows. The low-level text coordinates, float tolerances (0.5), and stream events from pdf2json are completely abstracted away.
3. Database ORM: Prisma abstracts raw SQL statements (SELECT, JOIN, INSERT) behind high-level declarative TypeScript APIs."

Q12 "How does TypeScript's Interface Declaration Augmentation demonstrate OOP concepts?"
💬 Interview-Ready Answer
"In types/next-auth.d.ts, we use TypeScript's Declaration Merging / Interface Augmentation:
```typescript declare module 'next-auth' { interface Session { user: { id: string; role: string; status: string } & DefaultSession['user']; } } ```
This represents Interface Extension (Inheritance): we inherit the base DefaultSession['user'] contract (name, email, image) and extend it with our domain-specific attributes (role and approval status). This enforces compile-time type safety across all consumers of session.user without altering the upstream NextAuth package."

Q13 "What OOP anti-patterns exist in your current codebase and how would you fix them?"
💬 Interview-Ready Answer
"I identified two classic anti-patterns during code review:
1. God Object / Monolithic Function: markAttendance() in actions/attendance.ts is 450 lines long and handles 9 gates, token extraction, IP parsing, atomic writes, and proxy alerts. Fix: Refactor into the Chain of Responsibility Pattern.
2. Anemic Domain Model: Our Prisma models are plain data bags with no behavior. All domain logic lives in separate procedural Server Actions. Fix: Wrap Prisma models in Rich Domain Entities (e.g. StudentEntity.canScan(session), SessionEntity.hasExpired()) to keep business rules colocated with the data they govern."
Q14 "Can you give an example of the Liskov Substitution Principle (LSP) in ScanX?"
💬 Interview-Ready Answer
"LSP states that objects of a superclass should be replaceable with objects of its subclasses without breaking application behavior.

- Where followed: In our authorization system, ADMIN, FACULTY, and STUDENT can all be passed to getServerSession() and satisfy the User contract.
- Subtle violation to be aware of: In lib/auth.ts, a GUEST user is synthesized without a genuine email (assigned @event.scanx.local) and with artificial enrollment numbers (EVT-XXXX). If downstream functions expect a real institutional email or genuine student roll number without checking role types, substituting a Guest where a Student is expected could lead to silent formatting errors."
📂 Code Reference
lib/auth.ts L101-L107
Q15 "Next.js App Router is heavily functional. Why combine it with OOP?"
💬 Interview-Ready Answer
"Modern full-stack development is multi-paradigm. Functional programming and Object-Oriented programming excel at different layers:

- Functional at the Boundary: React Server Components and Server Actions work best as stateless, pure, side-effect-free input/output pipelines. Server Actions act as thin HTTP controllers.
- OOP in the Core Domain: Behind the Server Action boundary, complex business domains (like device binding rules, multi-gate validation pipelines, and role access matrices) are much more maintainable when modeled with OOP classes, encapsulation, and design patterns.

This gives us the best of both worlds: clean, reactive Next.js web endpoints calling robust, encapsulated OOP domain services."
